# Key management

*The keys and secrets a node pool operator handles, where each one lives, and what happens if you lose or rotate one.*

## The keys

| Key | Purpose | Where stored |
|---|---|---|
| **Node identity** | The node's ID. The node pool's share tags commit to it, and ghost-mining's template-server key is derived from it | `/home/ghost/.ghost/node.key` |
| **SV2 pool authority keypair** | The identity pool_sv2 presents to SV2 miners and the translator; SV2 miners may pin its public key | `/etc/ghost/pool-config.toml` (root-only, 600) |
| **Fee address** | Receives the transaction fees of blocks this node's miners find | Your own wallet; only the address is on the node, in `pool-config.toml` |
| **Internal API secret** | Authenticates internal API calls, such as from the node dashboard | `/etc/ghost/pool.toml` (`[network] internal_api_secret`) |
| **Signing key** | Generated by the installer and kept across re-runs | `/etc/ghost/pool.toml` (`[network] signing_key`) |
| **RPC password** | ghostd's RPC credentials | `/etc/bitcoin/bitcoin.conf`, regenerated on every installer run |

The installer generates all of these on the machine; nothing is shared with any other node. See [Deployment](#deployment).

There is no treasury key for an operator to hold. The treasury is a fixed protocol address, the same for every node.

## Node identity

An Ed25519 keypair plus a small proof of work. Once generated, this key is your node.

### Generate

The installer does this for you, and keeps an existing key on a re-run. By hand:

```bash
ghost-mining --generate-identity
```

### Inspect

```bash
ghost-mining --show-identity
```

```
Node ID:   a1b2c3d4e5f6...
Short ID:  a1b2c3d4
Signer:    local
```

The Short ID is the first 4 bytes, used in logs.

### Storage

```bash
chmod 600 /home/ghost/.ghost/node.key
chmod 700 /home/ghost/.ghost
```

- **Back it up.** Nothing on the machine backs it up for you. Lose it and the node becomes a different node.
- **Don't share it between nodes.** Each node has its own identity.
- **Don't commit it anywhere, or copy it over unencrypted channels.** Encrypt it (for example with `age` or GPG) before it leaves the machine.

### HSM and KMS signers

ghost-mining can also keep the identity in a PKCS#11 HSM or a cloud KMS instead of a file:

```toml
[identity.signer]
type           = "hsm"
library_path   = "/usr/lib/pkcs11/libsofthsm2.so"
slot           = 0
pin_env        = "HSM_PIN"
key_label      = "ghost-node-key"
```

```toml
[identity.signer]
type     = "kms"
provider = "aws"
key_id   = "arn:aws:kms:us-east-1:123456789:key/abcd-1234"
```

A KMS puts the cloud provider in your trust circle. The installer only sets up a file-based key.

## SV2 pool authority keypair

Generated fresh at install, per node, and written to `/etc/ghost/pool-config.toml`, which only root can read. A re-run of the installer reads it back and reuses it, so SV2 miners that pinned the authority public key keep working. If you replace it, every SV2 miner that pinned the old key must be updated.

## Fee address

Not a key on the node: only the address is stored, as `[node_pool] fee_address` in `/etc/ghost/pool-config.toml`. Keep its private key in your own wallet, ideally offline. It must be P2SH, P2WPKH, P2WSH or P2TR on the node's network. To change it, re-run the installer with `--fee-address`.

Miners are not paid through it. It only ever receives the transaction fees of blocks this node's miners find.

## Internal API secret

A 64-hex-character secret the installer generates. Mainnet refuses to start without it. The installer also writes it to the root-only `/etc/ghost/dashboard-internal-auth.env`, which the dashboard reads through `EnvironmentFile=`, so a dashboard installed later uses the same value. If you change it by hand, update both.

## Rotation

| Key | Rotate when | Effect |
|---|---|---|
| Node identity | Only for a real reason: the key leaked or a backup was compromised | The node gets a new ID and is a different node from then on |
| SV2 authority keypair | The secret leaked | SV2 miners that pinned the old public key must be updated |
| Fee address | Whenever you like | Re-run the installer with `--fee-address`; applies once `sri-pool` runs with the new config |
| Internal API secret | On a schedule, or if it leaked | Update the dashboard drop-in too |

Rotating the node identity by hand:

```bash
sudo systemctl stop sri-translator sri-pool ghost-mining
sudo -u ghost cp /home/ghost/.ghost/node.key /home/ghost/.ghost/node.key.retired-$(date +%Y%m%d)
sudo -u ghost rm /home/ghost/.ghost/node.key
sudo -u ghost /opt/ghost/bin/ghost-mining --config /etc/ghost/pool.toml --generate-identity
```

Then re-run the installer with the same flags as before: ghost-mining's template-server key is derived from `node.key`, and pool_sv2 pins it, so pool_sv2's config must be regenerated to match.

## Backups

| Key | Backup |
|---|---|
| Node identity | Encrypted copy of `node.key` off the machine, after generation |
| SV2 authority keypair | Encrypted copy of `pool-config.toml` off the machine |
| Fee address | Your wallet's own backup (seed phrase) |
| Internal API secret | Your secret manager; it can also be regenerated |
